# Asset Scanning Documentation Scope Audit (Stage 1)

## Summary

Both features were verified against the current state of the two worktrees (`repo/cli-plugins-pr217`, branch `feat/Asset-Scanning-v1`, and `repo/cli-plugins-pr294`, branch `feat/Asset-Scanning`). Most of the prior research holds up, including the stale `--data-dir` message in GA's `assets.ts`. Verification also surfaced several new findings that materially affect what should be documented, the most important being that the "auto-detect the `assetsScan` org-plan flag and set `skipAssetsPublish`" mechanism appears to be dead code in both worktrees as currently checked out: the trigger that would populate it is never set anywhere in either repo, and the `isFeatureEnabled`/`FeatureCtx` helpers it calls do not exist in the installed `@contentstack/cli-utilities@1.18.5` dependency. This needs engineering confirmation before Stage 3/4 documents that behavior as working. The recommendation on both open questions in the brief is to agree with the stated default hypotheses: update existing command docs rather than create new files, and give `Beta/bulk-operations-in-cli.md` its own inline Limitations section rather than a new Beta limitations file.

### New-file vs. update-existing decision

**Agree with the hypothesis: update existing docs, do not create a new file.** Reasoning:
- Neither GA change adds a new command. `--backup-dir` is a new flag on the already-documented `cm:assets:publish`, and the scan-gating on import is new behavior inside the already-documented `cm:stacks:import`.
- The repo's established convention for related command variants is one file per command-group (`bulk-publish-and-unpublish-content.md` already documents `cm:assets:publish`, `cm:entries:publish`, and multiple flag combinations of each in the same file, under separate `###` subsections). Asset scanning fits this pattern as another `###`-level flag addition.
- `feature-doc.md`'s required Troubleshooting section and `common-rules.md`'s Limitations definition assume limitations and troubleshooting are attached to the doc describing the affected command, not to a standalone doc about the underlying detection mechanism. Since GA already centralizes limitations in `cli-limitations.md`, the correct location for limitation-level content is that existing file, organized by the same module headings already in use (`Bulk Publish/Unpublish Limitations`, `Import Setup Limitations`), not a new "Asset Scanning" limitations file.

## New gaps found (not in the prior known findings)

1. **Confirmed and precisely located:** GA's `contentstack-import/src/import/modules/assets.ts` line 96 tells the user to run `csdx cm:assets:publish --data-dir ${this.importConfig.backupDir} ...`, but the actual flag is `--backup-dir` (defined in `publish.js` lines 192-196). GA's `commands/cm/stacks/import.ts` line 203 has the correct `--backup-dir` reminder. This is a real, user-facing inconsistency: users who trust the message from `assets.ts` (printed at the end of the `assets` module's own `start()`, distinct from the import command's closing summary) will pass a flag that does not exist on `cm:assets:publish`. Needs an explicit Troubleshooting entry in GA docs so users are not misled, per the task's callout.

2. **New:** GA's `import.ts` closing reminder (line 201: `if (!result?.noSuccessMsg && assetsImported && importConfig.skipAssetsPublish)`) fires whenever `skipAssetsPublish` is true for any reason, including when a user manually passes `--skip-assets-publish` with no asset scanning involved at all. The printed message unconditionally says "assets were imported but not published asset scanning is enabled and must complete first" (line 203), which is misleading in the manual-flag case since scanning may not be enabled. Worth a Troubleshooting entry: "I see an asset-scanning message but my org doesn't have asset scanning" with the actual root cause (the message is not conditioned on `assetScanningEnabled`, only on `skipAssetsPublish`).

3. **New, significant for docs accuracy:** In GA's `asset-scan.js`, `SCAN_RETRY.MAX_RETRIES` is hardcoded to `0` (line 11). In `resolveInQueueAssets` (lines 54-113), the retry loop (`for (let attempt = 0; attempt < SCAN_RETRY.MAX_RETRIES ...)`) therefore never executes, so pending/in-queue assets are immediately treated as unresolved and skipped, logging "Asset scan: N asset(s) remained in queue after 0 retries and will be skipped" and "Skipped (max retries exceeded)" for each. This directly contradicts the function's own doc-comment, which describes "5 attempts total, max 155s" backoff. Documentation should describe the actual behavior (no automatic retry, manual republish required) rather than the aspirational comment. This is important enough to state as core Main Content behavior, not only a Troubleshooting note.

4. **New:** In Beta's `bulk-assets.ts`, the `--dry-run` flag (lines 54-57) is only read inside `runDataDirFlow()` (line 123, checked at line 177). The default live-folder-scan `run()` method (lines 62-120) never reads `dryRun` at all. So `--dry-run` silently has no effect unless combined with `--data-dir`. This was not called out in the prior known findings and should be stated explicitly in the Beta flag documentation to prevent users from assuming `--dry-run` previews a normal (non-data-dir) publish/unpublish run.

5. **Correction to prior known findings:** The claim that Beta's data-dir file layout "errors if missing" for all three files (`assets.json`, `environments.json`, `mapper/assets/uid-mapping.json`) is only partly right. In `data-dir-asset-fetcher.ts`'s `scanDataDirStats` (lines 28-63), only a missing `assets.json` throws (line 38-42). A missing `uid-mapping.json` or `environments.json` only logs a warning and continues with degraded behavior (empty mapper means all assets get skipped later, environments fall back to raw UIDs as names). This is worth stating precisely per file in the docs rather than as a blanket "errors if missing."

6. **New contrast between GA and Beta:** GA's `getAssetsFromBackup` (in `producer/publish-assets.js`, lines 273-280) does hard-throw for a missing `uid-mapping.json` or missing `environments.json` on the `cm:assets:publish --backup-dir` path. This is the opposite leniency from Beta's `--data-dir` path (item 5). Since both features use a similar backup/data-dir concept, documenting this GA/Beta behavioral difference explicitly (rather than assuming they behave the same) would prevent user confusion for anyone using both versions.

7. **New, potentially major:** Beta's `module-importer.ts` defines a private method `detectAssetScanning(orgUid)` (lines 198-206) that checks both `assetsScan` and `amAssetsScan` plan features. Searching the whole Beta package tree found no call site for this method anywhere, it is dead code. The actual live import-time gating decision comes only from `import-config-handler.ts`'s `config.planStatus['assetsScan']` check (line 165 GA / 199 Beta), which does not consider `amAssetsScan`. Documentation should not imply that `amAssetsScan` currently affects the live asset-publish-skip gating decision on import, only that it is checked in unreachable code.

8. **New, open question significant enough to flag prominently:** Both GA's and Beta's `import-config-handler.ts` (and the equivalent `export-config-handler.ts`) read `context?.planCheckRequired` (GA line 145, Beta line 179) to decide whether to run the deferred `isFeatureEnabled('assetsScan', ...)` plan check that would populate `config.planStatus` and, from there, `config.assetScanningEnabled`/`skipAssetsPublish`. A repo-wide search (both worktrees, both `contentstack-import` and `contentstack-export`) found no place that ever assigns `context.planCheckRequired`, so `deferredFeatures` is always an empty array and this whole plan-check block never runs. Separately, `isFeatureEnabled` and `FeatureCtx` are imported from `@contentstack/cli-utilities` but do not appear anywhere in the resolved installed dependency (`@contentstack/cli-utilities@1.18.5`, matching the `~1.18.5` range in both `package.json` files) in either worktree's `node_modules`. Together, this suggests the org-plan auto-detection path described in the task background may not be functional in the current checked-out state of either branch. See Open Questions below, this needs direct engineering confirmation before Stage 3/4 documents "asset scanning auto-detected from the org plan" as current, working behavior.

9. **New:** GA's `bulk-publish-and-unpublish-content.md` has no `## Troubleshooting` section anywhere in the file today (confirmed by heading scan). Adding the stale-flag-message and disabled-retry Troubleshooting entries (items 1 and 3 above) means introducing a new `## Troubleshooting` heading into this file, which is a larger structural addition than a single new entry in an existing section. Flagging this so Stage 2/3 scopes the work correctly.

10. **New:** GA's `import-content-using-the-cli.md` has `## Limitations` (line 689) positioned before `## Troubleshooting` (line 693), the reverse of `common-rules.md`'s specified order. Beta's `bulk-operations-in-cli.md` has no `## Next Steps` section at all. Both are pre-existing structural issues unrelated to asset scanning, called out here only because new content is being added to these same files and a future stage may need to decide whether to fix the ordering while it is in there, or leave it untouched as out of scope.

## Open questions / needs human confirmation

1. **RESOLVED (engineering confirmed, verified against code).** Is the org-plan `assetsScan` auto-detection actually functional today? Answer: not yet, it is genuine in-progress work, not dead code. The utilities-side plan-check logic (`isFeatureEnabled`, `FeatureCtx`, and a prerun hook that sets `context.planCheckRequired`) lives in `repo/cli-pr2646` (confirmed present at `packages/contentstack-utilities/src/feature-status/` and `packages/contentstack/src/hooks/prerun/plan-guard.ts`), and has not yet been merged into the `@contentstack/cli-utilities@1.18.5` that `cli-plugins-pr217`/`cli-plugins-pr294` depend on. Each plugin will declare which plan features it needs checked via its own `package.json`, and `context.planCheckRequired` will be populated from that once the utilities update ships. Docs decision: describe the org-plan auto-skip as the intended/rolling-out behavior, not as something already fully active end-to-end in the current GA/Beta releases. Exact wording to be confirmed during Stage 2 drafting rather than guessed.

2. **RESOLVED (engineering confirmed).** Does asset scanning apply to CS Assets (space-based) stacks at all? Answer: no, not currently. Engineering confirmed scanning does not apply to CS Assets today, and a plan-key check for CS Assets is future scope, not part of either of these two branches. Docs decision: no change needed to `cli-for-cs-assets.md` for this round, matches the "no change needed, with a caveat" recommendation already in this audit. The caveat is resolved, not just unconfirmed.

3. **Downgraded from open question to a drafting instruction, no longer blocking.** Exact wording/UX of the Beta "Asset Scan Status" dashboard was read from source (`printScanningDashboard`, `bulk-assets.ts` lines 304-332, and message strings in `messages/index.ts` lines 215-231), but not run for real, so exact column alignment and line breaks are unconfirmed. Resolution: Stage 2 must not present this as a verbatim captured screenshot. Describe the dashboard's fields and ordering in prose (confirmed from source) and, if a code block is used, label it as illustrative rather than an exact terminal capture. This removes the need for a real CLI run.

4. **RESOLVED by direct code trace (no engineering input needed).** `--retry-failed` and scan-status interaction on Beta's `cm:stacks:bulk-assets`. Traced `revert-retry-handler.ts`, confirmed the retry path rebuilds its item list from `readBulkFailedLog`/`readSingleFailedLog` log entries only, it never calls `fetchAssets` (the function that performs `include_asset_scan_status`). So Beta's retry-failed does not re-check scan status, same as GA's explicit documented behavior. Docs decision: state this directly as confirmed Beta behavior, mirroring GA's existing note.

5. **Still open, low priority, cosmetic only.** Exact intended default/behavior of Beta's `maxPolls`/`pollInterval`: `config/index.ts` sets `pollInterval: 2000` and `maxPolls: 300` with a comment claiming "~1 minute," but 300 x 2000ms computes to 600,000ms (10 minutes). This is a source comment bug, not a docs blocker: if a maximum poll-wait time needs documenting, use the computed 10 minutes, not the comment's "~1 minute." Does not need engineering confirmation before Stage 2, the computed value is verifiable arithmetic, not a behavior guess.
